# Marketing Feedback Source

## 1. Purpose

This document captures marketing team feedback and turns it into structured product and UX analysis.

This is not an implementation task list.
This is not a redesign brief.
This is a structured input layer for evaluating the current OptiVideo prototype.

The goal is to understand the marketing intent before proposing any product, UX, UI, copy, IA, or flow changes.

## 2. How to Use This Document

1. Paste raw marketing feedback into Section 3.
2. Preserve original wording and meaning as much as possible.
3. Do not summarize too early.
4. Analyze feedback themes.
5. Extract the marketing team's thinking model.
6. Compare feedback against the current prototype.
7. Identify UI, UX, userflow, copy, messaging, IA, and trust gaps.
8. Propose solution options.
9. Split any accepted solutions into small implementation phases.
10. Implement only after explicit approval.

## 4. Feedback Analysis Framework

For each feedback item, analyze:

### 4.1 Surface Request

What is the stakeholder literally asking for?

### 4.2 Underlying Need

What problem, concern, or goal is behind the request?

### 4.3 Marketing Thinking Pattern

Classify the feedback into one or more patterns:

- Clarity: user should understand faster
- Value visibility: product value should be obvious earlier
- Conversion: user should be pushed toward action
- Demoability: the flow should be easier to explain or show
- Trust: user needs proof, safety, transparency
- Performance framing: connect feature to ROAS, campaign quality, feed quality, or business outcome
- Simplicity: reduce cognitive load
- Control: user wants more control over output
- Confidence: user needs to know what will happen before committing
- Brand/storytelling: experience should communicate Optifeed's positioning
- Operational feasibility: team wants something easier to sell, explain, or support

### 4.4 Prototype Alignment

Evaluate:
- Already aligned
- Partially aligned
- Not aligned
- Not relevant
- Out of scope

### 4.5 Risk of Literal Implementation

If we implement the feedback exactly as written, what could go wrong?

Classify:
- Low risk
- Medium risk
- High risk

Examples:
- Adds complexity
- Breaks existing flow
- Creates visual clutter
- Conflicts with design.md
- Conflicts with previous UX decisions
- Requires backend
- Requires real data
- Low demo value

### 4.6 Better Product Interpretation

Rewrite the feedback as a product problem statement.

Format:
Marketing said: "[raw feedback]"
Product interpretation: "Users need to understand, feel, decide, or do X because Y."

### 4.7 Suggested Response

Choose one:
- Implement as-is
- Implement a smaller version
- Reframe before implementing
- Defer
- Reject as out of scope
- Needs more context

## 7. UI/UX/Userflow Problem Detection

When feedback is analyzed, identify problems in these categories:

### 7.1 Information Architecture Problems

Examples:
- Navigation hierarchy unclear
- Sidebar labels confusing
- Screen purpose unclear
- Feature/module relationship unclear

### 7.2 Userflow Problems

Examples:
- User does not know what happens next
- User cannot recover from a state
- Too many actions appear at once
- Primary path is visually weak
- Flow feels more like a dashboard than a guided product experience

### 7.3 UI Problems

Examples:
- Important button not visible
- Too much visual noise
- Controls compete with each other
- States are not clear

### 7.4 Copy and Messaging Problems

- Label does not match destination
- Product value is abstract

### 7.5 Trust and Conversion Problems

- User does not know token cost
- User does not know what will be generated

## 9. Implementation Rules for Feedback-Based Changes

- Never delete large components.
- Never rewrite screens from scratch unless explicitly approved.
- Never implement raw feedback directly without analysis.
- Always preserve the demo-ready state.
- Every implementation must be phased.
- One phase at a time.
- Build and lint after every phase.
- 0 new lint issues.
- Stop after every phase and request approval.
- Prefer the smallest safe change.
- Do not add backend, API, payment, real integrations, real AI generation, real ZIP, or real channel sending.
- Do not expand scope beyond frontend prototype unless explicitly approved.

## 10. Feedback-to-Phase Workflow

Phase naming:

- MFA0: Feedback ingestion and classification
- MFA1: Marketing thinking model
- MFA2: Prototype compatibility analysis
- MFA3: UI, UX, and userflow issue map
- MFA4: Solution proposal map
- MFX0+: approved implementation phases only

MFA phases are analysis-only.
MFX phases are implementation phases.
No MFX phase can start without approval.

### Item 1 — Textile templates should be detailed video scripts, not simple prompts

**Surface request:**
Replace short template descriptions with full cinematic scenario text — a model walking on an outdoor shopping street like Bağdat Caddesi, wearing accessories, surrounded by stores.

**Underlying need:**
Users need to understand exactly what video they will get before committing tokens. Abstract template names do not create confidence. Concrete scenario descriptions reduce decision anxiety and communicate value before any commitment is made.

**Marketing thinking pattern:**
Confidence, Clarity, Demoability

**Related prototype area:**
Template selection, TemplateCard component, templates data file

**Prototype alignment:**
Partially aligned. Current templates use scenario-based names. However, the description text in each TemplateCard is short and does not read as a full scenario. The "script" that would inform generation is not visible to the user at any point in the flow.

**Risk of literal implementation:**
Medium. Enriching template description copy is low risk and purely editorial. Making the scenario text the actual AI generation prompt requires backend integration and is out of scope. Risk: if the UI describes a detailed scene but the sample video doesn't match, users will feel misled during demo.

**Product interpretation:**
Marketing said: "Templates should be detailed video scenarios, not simple commands."
Product interpretation: "Users need to feel certain about what they will get before spending tokens, because abstract template names do not create enough confidence to trigger a commitment."

**Suggested response:**
Implement a smaller version. Enrich template description copy with scenario-level detail. Do not expose or simulate raw AI prompt text.

### Item 2 — Textile videos should include pause moments and multiple angles

**Surface request:**
Template scenarios should include directional choreography: the model pauses, turns left and right so front and back of the garment are both visible. A 1-2 second static moment should be part of every textile video.

**Underlying need:**
Textile products must be evaluated from multiple angles. A video showing only forward motion fails to communicate fit, silhouette, and back detail. This is a product quality and trust concern — a video that doesn't show the clothing clearly will not be approved for campaign use.

**Marketing thinking pattern:**
Trust, Value visibility, Performance framing, Control

**Related prototype area:**
Template selection (what the template promises), Video preview modal (what the user sees), Generate-review

**Prototype alignment:**
Not aligned at the video content level — the sample video is static and cannot be changed. Partially aligned at the template description level — this choreography language could be added to template copy to communicate what the scenario delivers.

**Risk of literal implementation:**
High. Actual video choreography (pause, turn, angle) is an AI generation constraint, not a frontend constraint. Describing it in copy is feasible. Promising it in the UI without the video output matching creates a trust gap during demos and live use.

**Product interpretation:**
Marketing said: "Templates should include pause moments and front/back angle turns."
Product interpretation: "Users need to trust that the generated video will actually show the product from all relevant angles, because a single-angle or continuous-motion video does not prove garment quality and will not be approved."

**Suggested response:**
Reframe before implementing. Template descriptions can include choreography language ("180 derece tur", "duraklamalı senaryo"). The actual video behavior is backend/AI scope. Copy must not overpromise what the current sample video cannot demonstrate.

### Item 3 — Videos should be 8-10 seconds long

**Surface request:**
AI-generated videos should be 8-10 seconds. The shot should include the model walking from a distance toward the camera and then showing the product fully.

**Underlying need:**
Marketing needs output specifications to plan for channel compatibility. Meta video ads, Google PMax, and TikTok all have minimum duration requirements. Knowing the duration before generating creates confidence and removes a post-production question.

**Marketing thinking pattern:**
Confidence, Performance framing, Clarity

**Related prototype area:**
Template selection, Confirm screen, Generate-review, Video preview modal

**Prototype alignment:**
Not aligned. The current sample video has no stated duration. No duration information appears anywhere in the UI.

**Risk of literal implementation:**
Medium. Adding "8-10 sn" to template descriptions and the Confirm screen is copy-only and low risk. However, if the sample video is noticeably shorter or longer than 8-10 seconds, the stated spec creates a credibility gap during demos.

**Product interpretation:**
Marketing said: "Videos should be 8-10 seconds long."
Product interpretation: "Users need to know the output format before generating, because channel delivery requirements and creative expectations depend on predictable video length."

**Suggested response:**
Implement a smaller version. Add duration range to template card descriptions and/or the Confirm screen. Do not add a duration UI control. Do not apply this to the sample video without confirming the actual clip length matches.

### Item 4 — Price and brand overlays should not be generated by AI

**Surface request:**
AI generates only the visual video. Text overlays — price, brand name, campaign copy — are added separately through Dynamic Creative. These should never appear in the AI-generated video.

**Underlying need:**
AI text generation in video is unreliable: fonts are wrong, text is hallucinated, or placement is broken. Editable text layers through Dynamic Creative give the user control, accuracy, and reusability. This also defines the product boundary between OptiVideo and Dynamic Creative and prevents user confusion about which tool does what.

**Marketing thinking pattern:**
Control, Trust, Operational feasibility, Brand/storytelling

**Related prototype area:**
Template selection, Confirm, Generate-review, Export, Dynamic Creative sidebar link

**Prototype alignment:**
Aligned in implementation — the current prototype generates only a visual video with no text overlay. However, the prototype does not explicitly communicate this boundary anywhere. Users who expect a complete ad creative (with price and branding) may not understand that Dynamic Creative is the next step.

**Risk of literal implementation:**
Low. The technical boundary already exists. This is a copy and messaging gap, not an implementation gap.

**Product interpretation:**
Marketing said: "Price and brand overlays should not be generated by AI."
Product interpretation: "Users need to understand that AI Video generates the scene layer only, and Dynamic Creative adds the text layer, because conflating these two creates uneditable errors and breaks the handoff workflow."

**Suggested response:**
Implement a smaller version. Add a short explanatory note in the Template selection or Confirm step that makes the AI Video / Dynamic Creative boundary explicit.

### Item 9 — Generated but unapproved videos should not disappear

**Surface request:**
Videos that have been generated must persist — in the folder or as drafts — even if the user has not yet approved or rejected them. Token spend must not result in invisible or lost output.

**Underlying need:**
Token spend creates user accountability and expectation. If a generated video disappears because the user navigated away, refreshed, or closed the tab, the platform is perceived as losing the user's money. This destroys trust and generates complaints. Persistence implies the platform is safe and responsible with user resources.

**Marketing thinking pattern:**
Trust, Control, Confidence

**Related prototype area:**
Generate-review, Library, FolderCard, setup_in_progress status

**Prototype alignment:**
Partially aligned. The generate-review step shows all videos including pending-review ones in the current session. The library shows folders with a `setup_in_progress` status. However, if the user navigates away from the generate-review step, session state is lost (Videos.tsx is in-memory useState). The library does not show pending-review video count or a "come back to review" prompt.

**Risk of literal implementation:**
Medium. True persistence requires a backend. In the frontend prototype, this can be addressed through copy and status labeling — communicating that videos are "saved" and the folder is "in progress" — without actual persistence. Risk: if users navigate away and return during a demo, the state will reset, breaking the persistence illusion.

**Product interpretation:**
Marketing said: "Generated but unapproved videos should not disappear."
Product interpretation: "Users need to trust that token spend creates durable, retrievable output — even if they don't immediately review, the generated videos must feel safe and accessible."

**Suggested response:**
Reframe before implementing. Use copy, status labels, and library UX to communicate persistence ("videolar kayıt edildi", "inceleme bekliyor") without requiring actual backend state. Flag the demo navigation risk separately.

## 13. Initial Pattern Summary

### What marketing optimizes for

1. **Confidence before commitment.** Users must understand exactly what they will get before spending tokens. This drives Items 1, 2, 3, and 5 — all of which are about making the template selection moment more informative and more concrete.

2. **Trust through transparency and safety.** Generated content must feel accountable, safe from errors, and recoverable. This drives Items 4, 9, and 10 — boundary clarity (AI vs DC), video persistence, and approval gating.

3. **Product positioning as a purpose-built platform.** OptiVideo must feel like a dedicated AI creative tool for textile merchants, not a generic AI video utility. This drives Items 6, 12, and 4 — template focus, sidebar grouping, and the AI/DC separation.

4. **Flow simplicity matching the merchant's mental model.** Entry via product catalog, campaign-level export, no folder-first friction. This drives Items 7 and 11 — both already aligned.

5. **Generation experience that feels alive and fast.** The waiting period should not feel frozen or passive. This drives Item 13 — already aligned.

### What marketing worries about

1. Token spend that produces no visible, usable, or recoverable output — lost investment with no recourse (Item 9).
2. AI-generated errors going live unchecked — legal and reputational liability for incorrect brand or price text (Items 4, 10).
3. Video output that does not show the product correctly — wrong angle, missing detail, hallucinated texture — resulting in unusable creatives (Items 1, 2, 8).
4. The product feeling abstract or hard to explain during sales demos — templates need to be concrete enough to sell themselves (Items 1, 5, 6).
5. Users not understanding the two-tool workflow: AI Video generates the scene, Dynamic Creative adds text (Item 4).

### What marketing may underestimate

1. **Frontend-only constraints.** Multi-image AI input (Item 8), real video choreography and duration (Items 2, 3), and true state persistence (Item 9) all require backend. They cannot be fully delivered in the current prototype.

2. **The gap between describing a scenario and delivering one.** Marketing writes "model walking on Bağdat Caddesi with accessories" — the sample video cannot change to match. If the description and the video diverge, demo credibility is damaged, not improved.

3. **Hover preview interaction complexity.** Item 5's hover video preview sounds simple but involves autoplay state management, multiple video instances potentially running simultaneously, and performance risk on lower-end hardware.

4. **Bulk download scope ambiguity.** Item 15 seems simple ("just a download button") but raises several unresolved questions: approval gating, format, relationship to channel export, and whether a mock ZIP is appropriate in a prototype.

5. **The cost of too much information too early.** Several items (1, 2, 3) push toward showing more detail at the template selection stage. There is a risk of making the selection step heavier and more cognitively demanding when the goal is to reduce friction.
